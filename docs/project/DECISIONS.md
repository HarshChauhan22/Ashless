## 2026-09-16 — Foundation cleanup pass (pre-implementation)

Context: `docs/project/final-foundation-review.md` concluded **READY WITH CHANGES** — no CRITICAL conflicts, but one HIGH and several MEDIUM/LOW inconsistencies needed resolving before coding. All resolved in this pass, documented below.

### D-001: Bottom navigation is five equal tabs, no raised center item
- **Decision**: The app's bottom nav is exactly five equal-weight tabs — Home · Wallet · Progress · Coach · Profile — matching PRD §H. There is no raised/FAB-style center "SOS" nav item.
- **Why**: `design/ux-flow.md` and `design/design-system.md` specified two different nav bars within the same design set (a leftover from an earlier, pre-reconciliation draft in `ux-flow.md`). `design-system.md`'s version already matched the PRD; `ux-flow.md` was the stale one.
- **Changed**: `design/ux-flow.md` §3 and its screen-inventory framing updated to match `design-system.md` §9 and PRD §H.
- **Overrides**: the raised-SOS nav pattern described in the pre-reconciliation draft of `ux-flow.md`. No product/UX decision was made here — this was a doc-sync fix, not a new design choice.

### D-002: Google Sign-In is cut from MVP
- **Decision**: MVP auth is phone + OTP only. Google Sign-In is documented as a V1-ready option (interfaces described in `security.md` §2.4 and `api-spec.md` §3.1) but is not built, wired, or exposed in the MVP client or backend.
- **Why**: PRD Functional Requirement 1 and `mvp-scope.md` item 1 already scoped MVP auth as phone+OTP only, and the UX design (`design/screen-specifications.md` SCR-03) already excluded a Google button. Only the architecture docs (`security.md`, `api-spec.md`) still described it as a built feature. This was inferable from three already-agreeing canonical documents (PRD, MVP scope, UX) rather than a genuinely new call, so it was made directly rather than escalated.
- **Changed**: `security.md` §2.4, `api-spec.md` §3.1 (`POST /auth/google` marked "Not in MVP"), `mvp-scope.md` §Q (added as V1 item 9).
- **Reopen this decision if**: user research or a business requirement later calls for lower-friction sign-up via Google — the endpoint shape is already documented and small to add.

### D-003: `craving_sessions.outcome` gets a real `'abandoned'` value
- **Decision**: `craving_sessions.outcome` enum is `'resisted' | 'smoked' | 'simulated_purchase' | 'abandoned' | 'unresolved'`. `'abandoned'` = the user actively exited a breathing exercise, AI coach session, or the Digital Smoking Room mid-flow without completing it (an expected, common, neutral outcome). `'unresolved'` is reserved for a session that never reached any terminal outcome at all (e.g., app killed before any exit path fired) — rare. Both are streak-neutral and never counted as relapse or resisted-craving in rollups.
- **Why**: `design/digital-smoking-room.md` and `docs/product/analytics.md` (the `craving_abandoned` event) already treated "abandoned" as a specific, load-bearing category; the DB schema had never actually defined it, leaving an implementer to guess whether `'unresolved'` meant the same thing.
- **Changed**: `docs/architecture/database-schema.md` §3.4 (enum + explanatory note).

### D-004: Payout-leg events added to the product analytics taxonomy
- **Decision**: `payout_succeeded` and `payout_failed` are formal analytics events, defined in `docs/product/analytics.md` (not just `system-architecture.md`'s internal representative table), plus a "Payout failure rate" KPI.
- **Why**: The two-leg collect-then-payout model (PRD §L.5a) makes payout failure a first-class, user-notified new failure mode with its own refund/reversal path — it needs to be observable at the product-analytics layer, not just implied by architecture docs.
- **Changed**: `docs/product/analytics.md` §T (Savings/Ledger table) and §U (KPIs).

### D-005: Age Verification is now formally SCR-04A
- **Decision**: The Age Verification screen (self-declared DOB, required by PRD §IX.8, positioned between OTP Verification and Smoking Profile Setup) is adopted into the PRD's own screen numbering as **SCR-04A**. No functional change to the screen itself — it was already fully specified in `design/screen-specifications.md`, just missing a formal ID in the PRD.
- **Why**: The design layer had filled this gap unilaterally in an earlier pass and explicitly flagged it as needing PRD backfill. Backfilling is a pure administrative fix, not a design decision.
- **Changed**: `docs/product/PRD.md` §H (IA diagram), §I (new SCR-04A spec section), Functional Requirement 14 (exception list). `design/ux-flow.md` and `design/screen-specifications.md` updated to reference SCR-04A instead of "gap-fill."

### D-006: PRD's Amount Confirmation CTA copy corrected to match the shipped design
- **Decision**: PRD §I SCR-16's CTA example is **"SAVE ₹24"** (uppercase), not the previous "Save ₹24 now" (sentence case).
- **Why**: The new brand-selection requirement's explicit flow step ("user sees 'SAVE ₹XX'") and the design system's uppercase-emphasis convention (reserved for exactly two labels in the product: "I WANT TO SMOKE" and "SAVE ₹[amount]") had already been implemented in `design/digital-smoking-room.md`; the PRD's own copy example was the stale one.

- **Decision**: The Craving Intervention Hub (PRD SCR-11) presents exactly three equal-weight options: 60-second breathing, Quick Distraction (new — PRD SCR-11a), and the Digital Smoking Room. "Talk to your AI coach" is no longer one of the Hub's three cards.

### Bugs found and fixed during implementation (not product decisions, logged for the record)
- **Idempotency-Key header vs. body mismatch**: `POST /api/payments` originally read `idempotencyKey` from the JSON body, but the client (`lib/api-client.ts`) sends it as an `Idempotency-Key` HTTP header per `api-spec.md`'s own documented convention — every payment attempt 400'd. Fixed by reading `req.headers.get("Idempotency-Key")` in `webapp/app/api/payments/route.ts`.
- **Mock payment provider state not shared across routes**: `webapp/lib/payment-provider.ts`'s `orders` map was a plain module-level variable; Next.js dev compiles each API route as its own bundle, so `/api/payments` (which creates an order) and `/api/payments/[id]/verify` (which reads it back) each got their own empty copy, and verification always 404'd. Fixed by persisting the map on `globalThis`, matching the pattern `lib/db.ts` already used for the same reason.
- Both were caught by walking the actual browser journey end-to-end before declaring the feature done — see the test report in the conversation for the full verification (duplicate-payment idempotency, duplicate-webhook idempotency, amount-tampering rejection, negative-quantity rejection, and the streak-preservation invariant were all explicitly re-tested after the fixes).

## 2026-09-16 — Move from the web prototype to a real, locally-running backend + mobile app

### D-012: Mobile client is React Native/Expo, not native Kotlin/Compose; backend is a real Postgres-backed NestJS API, run locally first, real payments deferred
- **Decision**: Per the project owner's explicit direction ("build the real app... first build and run locally then shift to cloud"), the project moves from the Next.js web prototype to two real, separate codebases:
  - **Mobile**: `mobile/` — Expo + React Native + TypeScript, **not** the native Android/Kotlin/Jetpack Compose stack the architecture docs originally specified (`project_quit_smoking_app` memory's "Stack recommended" line, never formally logged as a DECISIONS.md entry before now). Chosen explicitly by the project owner over native Kotlin for speed: it reuses the React component/hook patterns already proven in `webapp/`, produces a genuinely installable Android (and iOS) app, and is testable immediately via Expo Go on a physical phone with no Android Studio/emulator/Java setup required.
  - **Backend**: `backend/` — a real NestJS API backed by a real local Postgres 16 database (via Homebrew, database `ashless_dev`), using Prisma 5.22.0 as the ORM per `database-schema.md` §6, replacing the web prototype's in-memory `globalThis` store entirely.
- **Scope boundary (also explicit, asked and confirmed)**: the real backend implements the full financial-integrity model — server-computed amounts, `(user_id, idempotency_key)` and `source_payment_id` unique constraints, a `Serializable`-isolation transaction for the ledger write — but **keeps the mock payment provider**, not real Razorpay/RazorpayX. Real payment-provider integration needs actual merchant KYC credentials the project doesn't have yet and is Phase 6 work, unchanged from `ROADMAP.md`. The full documented schema's payout-leg columns, `savings_destinations`, `webhook_events`, fraud/reconciliation tables, and `analytics_events` are deliberately not implemented yet either — see `backend/prisma/schema.prisma`'s own header comment for the exact list of what's deferred and why.
- **What's real now vs. the web prototype**: a real signed JWT (not a bare `x-user-id` header) issued at login; a real Postgres row per user/profile/session/payment/ledger-entry, enforced by actual database constraints instead of application-only checks; a real installable mobile client instead of a browser tab. What's still mocked: phone/SMS OTP (still always `123456` — real Firebase/SMS needs a Firebase project and per-SMS cost not yet set up) and the payment provider itself.
- **Screens ported to mobile — update, same day**: after a pause for the project owner to test the first slice (Login, Home, Craving Hub, Breathing) on a physical Android phone via Expo Go, the remaining screens were ported in the same session: Quick Distraction (tap-to-expand accordion), the full Digital Smoking Room flow (Entry interstitial → brand picker → quantity → amount/pivot → UPI method picker → processing → success → post-payment timer → failure, all under `mobile/src/screens/smoking-room/`), Relapse Flow, Savings Goals, the real Track/Wallet/Profile tab bodies, and AI Coach (required one new backend addition: an `ai_messages` table + `/ai-coach` GET/POST endpoints, ported 1:1 from `webapp/lib/ai-coach.ts`'s rule-based responder including the crisis-keyword escalation). The mobile app now matches the web prototype screen-for-screen; the Profile screen omits the Savings Destination section (backend deliberately doesn't implement `savings_destinations` yet, per this same decision's scope boundary). `webapp/` remains available as the working reference but is no longer the only complete client.
- **Also logged here** (should have been its own entry earlier, backfilled now): the original "Stack recommended" note in project memory said native Kotlin/Compose; this decision is the actual, now-binding reversal of that, superseding it.
- **Verified locally**: full curl-based end-to-end test against the real backend — login → brand catalog → smoking-profile creation (₹200/pack of 10 → ₹20/stick) → craving session → payment create (₹60 for qty 3) → duplicate-create idempotency (same cached result) → verify → duplicate-verify idempotency (same result, no double-credit) → wallet (correct balance/activity/monthly stats) → streak (0 days, unaffected by the redirect — CRITICAL STREAK RULE holds against real Postgres) → relapse logged (streak-since timestamp correctly moves forward) → negative-quantity rejection → missing-idempotency-key rejection → pack-price fat-finger ceiling rejection. Mobile app's Metro bundler verified compiling cleanly for both iOS and Android bundle targets (1130/1128 modules, no errors); not yet manually exercised on a physical device or simulator (none available on this machine — Expo Go on a phone is the fastest path once the project owner is ready to test it).

## 2026-09-16 — Mobile app fixes/additions after first physical-device test pass

The fifth is a genuine product-decision reversal, logged below.

### D-013: Digital Smoking Room brand selection uses fixed catalog prices, not user-entered pricing
- **Decision**: Picking one of the 12 official reference brands (D-008) in the Digital Smoking Room now auto-fills a fixed per-stick price for that brand — the user never types a pack price, pack size, or per-cigarette price for a catalog brand. A `BRAND_PRICES` map (`mobile/src/lib/brandPrices.ts`) holds the 12 fixed prices; selecting a brand calls `POST /smoking-profiles` with that price directly, matching brand row + "Continue" pattern already established (D-011), skipping straight to Quantity.
- **This reverses a previously "Immutable"/architecture-level rule**: `database-schema.md` §3.3 and the original foundation review explicitly required that `cigarette_brand_reference` **never** be a pricing source — "the only authoritative price... is the selected `smoking_profiles.cost_per_stick_paise`" (user-entered), specifically because an earlier draft's admin-managed catalog pricing was flagged as a bug that broke the "mirrors your real spend" promise (PRD Immutable Rule 3). This decision knowingly reverses that: catalog brands now carry a platform-fixed price instead of the user's own reported price.
- **Why**: explicit, direct instruction from the project owner ("Do not ask the user to manually enter the cigarette amount/price... automatically get/use the price for that cigarette brand"), given as one of five scoped fixes after hands-on testing. Interestingly, this also brings the app closer to the *original design artifact* — `BrandSelection.dc.html` (D-011's source) itself showed fixed per-stick prices next to each catalog brand (Gold Flake ₹18, Classic ₹20, Wills Navy Cut ₹15, Four Square ₹12, "Marlboro Advance" ₹25) — those five prices are reused as-is (with "Advance" keeping D-011's trademark-safe name, not the real brand prefix); the other seven brands got reasonable fill-in prices with no artifact source.
- **Not reverted**: the underlying financial-integrity architecture is untouched — `amount_paise` is still always server-computed from `smoking_profiles.cost_per_stick_paise * quantity` at payment-creation time (payment-architecture.md §3.1's rule), never client-supplied. What changed is only *where the profile's own price number comes from* at creation time (a fixed catalog lookup vs. a manually typed number), not whether the server trusts the client for the payment amount — that guarantee is identical either way.
- **Custom/uncatalogued brands unaffected**: "I can't find my brand" still opens the manual pack-price/single-stick-price entry form, since there's no catalog price to look up for a brand outside the official 12.
- **Reopen this decision if**: the product later wants per-user real pricing back for catalog brands too (e.g. regional price variation) — would mean re-adding a price-entry step specifically for catalog selections, on top of the current one-tap flow.
- **Also implemented, same session** (routine fixes/additions, not decision reversals): an intro/splash screen (`mobile/App.tsx` + `SplashScreen.tsx`) shown briefly on cold app open; the Ashless icon + wordmark added to the Login screen (`AshlessLogo.tsx`, reproducing `brand/assets/ashless-app-icon.svg` via `react-native-svg` since RN can't load `.svg` files directly) plus a `KeyboardAvoidingView`/`ScrollView` fix so the "Send OTP"/"Continue" button is no longer hidden behind the keyboard; a new post-login **User Details** screen (First Name, Last Name, Gmail, Age, Gender) gating entry to the rest of the app until submitted, backed by new `User` columns (`firstName`, `lastName`, `email`, `age`, `gender`, `onboardingCompletedAt`) and a `PATCH /auth/profile` endpoint; the smoke-free streak (`insights.service.ts`'s `computeStreak` and `longestStreakDays`) now anchors to `onboardingCompletedAt` instead of `createdAt` when set, so the tracker genuinely starts counting from the moment onboarding finishes.
- **Verified**: full curl-based test of login → onboarding-incomplete streak anchor → `PATCH /auth/profile` field-validation rejection → successful onboarding submission → re-login reporting `onboardingComplete: true` → streak re-anchored to the onboarding-completion timestamp → smoking-profile creation via a catalog brand + fixed price (no manual entry).
